# PF・ログイン ACL・実行ワークフロー構想に対する敵対レビュー

- 期間: 2026-08-13 — 2026-08-13
- 範囲: commit `2a55535` の知識ベース全体。前提は「将来 PF として UI を持ち、裏でこの仕組みが動き、ログインアカウントの内容を ACL 付きでワークフローに載せる」
- 実施者: 同一セッションのエージェント。REV-00005 と同じ観点（運用整合・証拠能力・権限・並行）に、主体と認可と実行状態を足して再監査した

## きっかけ

[ADR-00019](../adr/00019-kernel-and-project-layers.md) で kernel / project の分離と、散在ソースからの `draft` evidence を決めた直後、運用者が次の構想を明示した。UI を持つプラットフォームの裏で本 KB を動かし、ログインしたアカウントのソースを反映し、ACL を加味しながらワークフローを回す。構造 CI が緑でも、この構想に対して現行決定は整合するか、を敵対的に見る。

## 指摘と再検証の結果

| # | 指摘 | 再検証 | 取り込み先 |
| --- | --- | --- | --- |
| P0-1 | 文書モデルに principal が無く、`owners` は認可に使われていない | **確認**。ADR-00002 の必須キーに認可が無い。`.github/scripts` と workflows で `owners` の参照は 0 件。ADR-00006 の Tier 1 は INDEX/GRAPH を全員向けにロードする | EVID-00026 / ADR-00020 §3 |

| P0-3 | アカウント連携の集約はソース ACL を kernel へ漏洩させる | **確認**。PB-00018 は引用を `evidence/` に残す。AGENTS.md は個人データを禁じ、構想はアカウント内容の反映を求める。書き込み先の読者範囲がソース ACL より広い | EVID-00027 / ADR-00020 §5 / OQ-00032 |

| P1-4 | リポ単位の権限（CODEOWNERS / branch protection）すら未整備 | **確認**。REV-00005 対応方針 3 が先行条件（公開化またはプラン変更）を既に置いている。文書 ACL はその上に乗る。下の層が無い | REV-00005 を改変せず参照 |

## 用語（本レビュー内）

| 語 | 意味 | 意味しない |
| --- | --- | --- |
| PF | AIDD を操作する将来の製品 UI | 案件の画面デザイン（Figma。PB-00016） |
| kernel | 本リポジトリの働き方 KB | ログイン中ユーザーの個人ストア |
| 文書 ACL | 文書ごとの閲覧・遷移権限 | Frontmatter の `owners`（連絡先） |
| 実行ワークフロー | 担当・待ち・ゲートを持つ状態機械 | playbook（手順の文章） |

## 対応方針

1. **今は git KB の不変条件を守る**。構想を実装しない。文書モデルに認可と実行状態を埋め込まない（ADR-00020）
2. **PF はクライアント**。読みと下書き提案と PR 作成まで。第二の文書正本を持たない
3. **アカウント由来の原文は kernel に載せない**。越境の確認は人間（ADR-00017 の延長）
4. **着工条件**は OQ-00030（主体）・OQ-00031（認可の置き場）・OQ-00033（実行状態の置き場）が人間に閉じること。OQ-00017（効果測定）が空のまま画面を足さない
5. 上記が終わるまで、Frontmatter 新キー・ACL タグ・ワークフローエンジン・本リポジトリへのアプリコードは増やさない

## 未対応の判断

- OQ-00029（コネクタの MCP/API 化）は、認可の置き場（OQ-00031）より先に閉じない。先にコネクタを足すと、漏洩経路だけが先に開く
- ADR-00019 の二層はリポジトリ境界として維持する。アカウント境界は足さない（足すなら後継 ADR）
- frozen の ADR-00001 / ADR-00002 は改訂しない。認可キーが要るなら後継であり、今は作らない

## 2026-08-13 取り込み

運用者が本レビューの批判を認め、仕様を明示した。認証は Okta。git では認証情報を利用しない。既存節は改変せず、閉じた論点だけをここに追記する。

| 指摘 | 閉じ方 |
| --- | --- |
| P0-1 / P1-2 / OQ-00030（主体は何か） | **Okta**。GitHub アカウントでも git の committer でもない。[EVID-00028](../evidence/00028-okta-auth-git-holds-no-credentials.md) / [ADR-00020](../adr/00020-platform-is-a-client.md) §3 |
| P0-1 / OQ-00031（認可をどこに置くか） | **git の外**（Okta が認証、PF が認可とソース ACL の加味）。Frontmatter に ACL を足さない。git は認証情報を持たない |
| P0-2（共有 INDEX/GRAPH） | 維持。clone した git は認証後に公開してよい面だけを置く。見えてはいけない観測は commit しない（ADR-00020 §4） |
| P1-5（Confused Deputy） | 維持。ソース取得は Okta セッションのある PF 側。このリポジトリのエージェントは Okta トークンを扱わない |

残る未決は、アカウント由来本文の昇格層（OQ-00032）、実行状態の置き場（OQ-00033）、PF が git に書くときの GitHub 主体（OQ-00034）、コネクタ（OQ-00029）、効果測定（OQ-00017）。着工条件から OQ-00030 / OQ-00031 は外す。

## 2026-08-13 汎用性

運用者は、話題の PF が**今利用しようとしている実装**であり、kernel は**特定の PF 製品や IdP 名に固定せず汎用**でありたいと明示した（[EVID-00029](../evidence/00029-keep-platform-contract-generic.md)）。直前の取り込みで「主体は Okta」と書いたのは、その時点の利用例である。契約は「git の外の IdP が認証する。git は認証情報を使わない。PF はクライアント」に戻す（[ADR-00020](../adr/00020-platform-is-a-client.md) §1・§3）。既存節は改変しない。
