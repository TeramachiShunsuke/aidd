## 主張

「小さく作って直す」は、変更コストが低いことを前提にした戦略である。前提が崩れる箇所——既存データを持つスキーマ、公開済みの契約、外部に露出したインターフェース——だけが事前設計に見合う。可逆な箇所で事前設計をすると、試して測るより遅く、しかも精度が低い。

## 観測

- 変更コストは箇所によって桁が違う。関数の実装を差し替えるのはコードの変更だけで済むが、1 億行入ったテーブルの分割はデータ移行・二重書き込み・切り戻し手順を伴う。同じ「設計変更」でも作業量と失敗時の被害が非対称である。
- 契約は利用者数に比例して変更コストが上がる。内部モジュールのインターフェースは呼び出し元を全部直せば済むが、外部公開した API やイベントスキーマは、利用者の改修完了を待たないと壊せない。
- 不可逆に見える変更を可逆な手順に**分解する技法**が存在する。[Parallel Change（expand / contract）](https://martinfowler.com/bliki/ParallelChange.html) は、新旧を並行稼働させてから旧を落とすことで、一発勝負の変更を複数の可逆なステップに変える。裏を返せば、この分解をしない限りその変更は不可逆である。
- 可逆な領域では実測が事前設計に勝ちやすい。インデックスの追加やパラメータ調整は、議論するより本番相当のデータで実行計画を取るほうが速く正確である。結果は再現可能な観測として残せる。
- 一方、不可逆な決定は後から評価できない。シャーディングキーやテナント分離方式は、選ばなかった案の結果が観測できないため、「なぜその案にしたか」を当時の前提ごと残さないと、数年後に再評価できない。

## 限界

「不可逆」の判定に定量的な閾値はなく、データ量・利用者数・組織の切り戻し能力に依存する。本リポジトリで実際のマイグレーション事例を計測したわけではない。また Parallel Change のような分解技法が使えるかどうかは、対象システムの二重書き込み耐性に依存し、常に適用できるとは限らない。
