## 主張

既存の働き方 ADR は新しいリポジトリへ適用するときに残すべきだが、案件の考え方（その製品で何を選んだか）と同じ `adr/` 一覧に混ぜると、読む対象が判別できず可読性が落ちる。文脈予算（[EVID-00009](00009-context-budget-is-finite.md)）も、関係ない決定を常時候補に入れて浪費する。

## 観測

- 本リポジトリの [INDEX.md](../INDEX.md) は ADR-00001 から ADR-00018 までを単一の表に並べ、scope（働き方か案件か）の列を持たない。現行の 18 件はすべて文書運用・検査・SDD 接続であり、製品ドメインの決定は 1 件もない。
- 置き場の境界は既に文章化されている。[ADR-00008](../adr/00008-sdd-bridge.md) は「他プロジェクトでも同じ判断を繰り返すか」を昇格条件にし、[ADR-00014](../adr/00014-implementation-spec-split.md) は案件限りの ADR を spec / 実装リポジトリ側へ送る。 [GUIDE.md](../GUIDE.md) も「このプロジェクト固有の詳細を持ち込まない」と書く。
- それでも適用時の作業は未決のまま残っている。[ledger/open-questions.md](../ledger/open-questions.md) の OQ-00016 は core / project の二層分離と初期化手段を問い、OQ-00021 は案件限り ADR の置き場所と体裁を問う。決定文書はあるが、新しいリポジトリへ「残す／混ぜない／どこに書く」の手順がない。
- 2026-08-13 の運用者の明示的な仮説: 新しいプロジェクトへ考察を適用するなら既存 ADR は残したい。一方で「プロジェクトの考え方」と「ワークフロー」の ADR が混ざると可読性が悪くなる。情報を人が揃えて evidence を書く前提から、働き方そのものを組み直したい、というもの。
- このリポジトリを案件リポへ丸コピーすると、ADR-00001（目錄分割）から ADR-00018（採番）までが、将来の製品 ADR と同じ `adr/` に並ぶ。INDEX の「決定と手順」は働き方 18 件＋案件 N 件になり、案件作業で読むべき行が埋もれる。

## 限界

実際の案件リポジトリへ適用した測定はない（検索時間・読み飛ばし率は未計測。OQ-00017）。「混ざると読めない」は INDEX の構造と運用者の仮説からの推論であり、混在一覧を被験者実験してはいない。案件リポ内で `adr/` を機能ディレクトリに分ける案の優劣も、ここでは言えない。
