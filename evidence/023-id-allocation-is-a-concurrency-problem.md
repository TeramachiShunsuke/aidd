## 主張

ID の衝突は「注意不足」ではなく、**採番という共有資源の確保を、調整なしに並行して行っている**ことから出る。対策は 4 系統しかなく、どれを選ぶかは「採番をいつ確定させるか」で決まる。本リポジトリでは `frozen` 文書の不変性（[ADR-003](../adr/003-frozen-immutability.md)）が選択肢の一部を塞ぐ。

## 観測

### 発生条件

2026-08-09 に 2 回起きた衝突（[REV-006](../reviews/006-lifecycle-self-review.md)）は、どちらも次の 3 条件が揃ったときだけ起きている。

1. 2 つ以上の作業が並行している
2. どちらも新規文書を作り、**ブランチ内で番号を先に確定**している
3. どちらもまだ main に着地していない

条件 3 が効いているのは重要で、**片方が main に入った瞬間に、もう片方は自分が衝突していることを知りうる**。つまり衝突が見えない窓は「両方が未着地である期間」に限られる。積み上げ PR はこの窓を意図的に長くする（親がマージされても子は main に届かないため、着地したつもりの番号が main にない状態が続く）。

### 対策の 4 系統

| # | 系統 | 採番の時点 | 代表例 | 本リポジトリでの可否 |
| --- | --- | --- | --- | --- |
| 1 | 番号をやめる（スラッグ・ULID） | 採番しない | 多くの docs-as-code | **不可**。既存 ID の改名は `frozen` 5 件を壊す |
| 2 | 採番を一元化する | マージ時に管理者が付ける | Rust RFC / Python PEP | 可。ただし文書間が ID で参照し合うため、確定時に全参照の書き換えが要る |
| 3 | 一意な外部番号を借りる | PR を開いた時点 | Rust RFC の代替案（PR 番号） | 部分的。1 PR で複数文書を作ると番号が足りない |
| 4 | 衝突を早く見せる | ブランチ内（現状のまま） | — | 可。予防ではなく検知 |

系統 1 が塞がれているのが本リポジトリ固有の事情である。`frozen` 文書は 1 バイトも変えられないため、ID の体系を移行できない。新規のみスラッグにする混成も考えられるが、参照する側から見て 2 種類の ID が並ぶことになる。

系統 3 は魅力的で、PR 番号は GitHub が一意に採番するため調整が要らず、PR を開いた直後に確定できる。しかし本リポジトリの PR は 1 本で 3〜7 文書を追加しており、1 PR = 1 番号の前提が成り立たない。

### 「マージ直前に CI が採番する」案の評価

系統 2 の自動化にあたる。技術的には実行可能で、書き換えの範囲も限定される。**新規 ID を参照するのはその PR 内の文書だけ**なので（main の既存文書は、まだ存在しない ID を参照できない）、書き換え対象は PR 内に閉じる。`frozen` 文書が巻き込まれることもない。

一方で 3 つの費用が確認できる。

- **フックの置き場がない**。GitHub でマージの瞬間に内容を書き換える正規の口はない。merge queue（`merge_group`）は検証しかできず、内容の変更はできない。実装するならボットが PR ブランチへ push して自分でマージすることになり、CI の再実行と権限（`contents: write`）が要る
- **レビュー済みの内容が承認後に変わる**。番号だけとはいえ、レビュー中に付いた「EVID-016 の観測が弱い」といったコメントは、対象がリネームされた時点で指し先を失う
- **[ADR-017](../adr/017-machines-record-facts-humans-decide-status.md) と衝突する**。機械が文書を書き換えないという線引きを、採番だけ例外にする理由づけが要る

### 検知の非対称性

系統 4 の範囲でも、**main を権威とみなせば片方は機械的に決まる**。main が既に持っている ID を、未着地の PR が別のファイル名で使っている場合、譲るのは必ず PR の側である（main は過去を書き換えない）。この場合に限り「修正方法が一意」という [ADR-013](../adr/013-check-grades.md) の error 条件を満たす。

未着地の PR 同士の衝突は、どちらが譲るべきかが機械には決まらない。PR 番号の大小で決める規約を置けば決まるが、それは規約の追加であって観測ではない。

## 限界

- 観測は 2 件の実例と 4 つの公開事例に基づく。並行度が上がったときの衝突頻度は測っていない
- 系統 3 に「PR 番号に文書ごとの枝番を付ける」変種があるが、可読性の劣化を評価していない
- 「マージ直前の CI 採番」を実際に実装して費用を測ったわけではない。フックの制約は GitHub のドキュメント上の事実、レビューコメントの指し先喪失は仕組みからの導出である
