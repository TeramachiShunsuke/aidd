## いつ使うか

エージェントに DB やインフラの作業をさせる前。既存の構成ドキュメントが古くて信用できないとき。「現在の構成をまとめた資料が欲しい」と言われたとき。

## 手順

1. 渡したい情報を 3 つに仕分ける（[ADR-015](../adr/015-infra-context-layers.md)）

   - **制約** — 守るべき条件。整合性モデル、分離方式、RPO / SLO
   - **契約** — スキーマ、マイグレーション、IaC 定義
   - **状態** — 実インスタンス、パラメータ実値、行数、コスト

2. **制約**が KB の ADR にあるか確認する。なければ [PB-002](002-write-adr.md) で書く。作業前に読ませるのはこれだけでよい
3. **契約**はリポジトリ内の定義ファイルを直接読ませる。内容を要約した Markdown を作らない
4. **状態**は文書にせず、取得コマンドを渡す。作業種別ごとに次を使う

   | 知りたいこと | 取得コマンドの例 |
   | --- | --- |
   | 適用済みのスキーマ | `psql -c '\d+ <table>'` / マイグレーション履歴テーブル |
   | クエリの実行計画 | `EXPLAIN (ANALYZE, BUFFERS) <query>` |
   | 実際のデータ量 | `SELECT count(*)` / 統計ビュー |
   | 稼働中のリソース | `terraform state list` / `terraform show` |
   | 実行中のワークロード | `kubectl get <resource> -o wide` |

   コマンドは各リポジトリの runbook に置き、KB には**取り方の型**だけを残す

5. エージェントには「制約は ADR、状態は実行して確認」と明示する。状態を推測で埋めさせない
6. 作業が可逆か不可逆かを判定する

   - 可逆（インデックス、パラメータ、サイズ）→ 事前設計せず、試して測る。測定値を [PB-001](001-add-evidence.md) で evidence にする
   - 不可逆（テーブル分割、シャーディングキー、リージョン、公開契約）→ 先に ADR を書く

7. 障害や負荷試験の結果は、構成が変わっても有効なので優先して evidence にする

## 検証

- KB に「現在の構成」を記述した文書が増えていない
- エージェントに渡した文脈が、ADR（制約）と取得コマンド（状態）に分かれている
- 不可逆な変更の前に ADR が存在する
- 取得できなかった情報が、推測ではなく [ledger/open-questions.md](../ledger/open-questions.md) に残っている

## 失敗時

- 構成図を求められた → 定義ファイルから生成する手段を探す。生成できないなら、その図は維持できないので作らない
- 権限やネットワークで状態を取得できない → 取得できない事実を open-questions に残す。推測値で進めない
- 既存の構成ドキュメントが大量にある → 全部を移植しない。「なぜそうしたか」だけを ADR に救出し、残りは削除する
- 監査で特定時点の証跡が要る → 手書きせず、生成物として出力する仕組みを別途決める
