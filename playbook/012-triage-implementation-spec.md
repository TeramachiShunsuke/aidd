## いつ使うか

ビジネススペックを受け取って実装に入る前。「詳細設計書をどこまで書くか」で止まったとき。既存の設計書が厚くて維持できなくなったとき。

## 手順

1. 対象を 1 つの塊として見ず、箇条書きにして分解する。1 行が「契約」「決定」「振る舞い」のどれかを判定する

   - **契約** — 他者と守る約束。API、テーブル、イベント、外部連携のフォーマット
   - **決定** — なぜその契約か。選んだ案と却下した案
   - **振る舞い** — 入力に対する出力。業務ルール、バリデーション、状態遷移

2. **振る舞い**の行を消す。文書に残さず [PB-013](013-start-tdd-from-examples.md) でテストにする。消せない行があれば、それは受け入れ条件が例まで落ちていない箇所なので、PdO に差し戻す
3. **契約**の行は、機械可読な定義（OpenAPI / マイグレーション / スキーマ）に置き換える。Markdown に同じ内容を書かない。図が要るなら生成する
4. **決定**の行に、次の 3 つのいずれかが当てはまるか確認する

   | 条件 | 例 |
   | --- | --- |
   | 共有境界がある | 他チームが実装前に合意する必要がある |
   | 不可逆である | 既存データを持つスキーマ、公開済みの契約 |
   | 選択肢が複数あった | 却下理由を残す価値がある |

5. どれも当てはまらない決定は**書かない**。当てはまるものだけ ADR にする
6. その ADR の置き場所を決める

   - 他の案件でも同じ判断を繰り返す → KB に [PB-002](002-write-adr.md) で書く
   - その案件限り → spec / 実装リポジトリ側に置き、KB には持ち込まない

7. KB に上げたものは [ledger/claims.md](../ledger/claims.md) に錨を付ける（[PB-008](008-bridge-sdd-spec.md) の方向 B）

## 検証

- 残った文書に「入力と出力の対応」が書かれていない（それはテストにある）
- 残った文書に DDL や JSON スキーマの本文が貼られていない（それは定義ファイルにある）
- 残った各項目に、上の 3 条件のどれかが対応づく
- KB に上げた ADR が `## 根拠` と `related` の両方に evidence を持つ（`build-graph.py` が検査する）

## 失敗時

- 分解できない行がある → 抽象度が高すぎる。具体例を 1 つ書いてみると、契約か振る舞いかが判明する
- 「念のため書いておきたい」が残る → 誰がいつ読むかを言えるか確認する。言えないなら書かない
- 消した情報が必要になった → テストか定義ファイルから読めるはず。読めないなら、そこは本当に決定であり ADR に昇格させる
- 実装スペックが厚いまま減らない → 上流の曖昧さのサイン。[templates/acceptance-examples.md](../templates/acceptance-examples.md) を PdO に渡す
