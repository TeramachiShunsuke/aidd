## いつ使うか

PdO が書いたビジネススペック（SDD リポでは requirements.md が正。以下「要件」）を受け取り、TDD（[PB-00013](00013-start-tdd-from-examples.md)）に渡せる受け入れ例まで詰めるとき。開発側が「例が足りない」と差し戻した項目を、まとめて上流で解消したいとき。

成果物は spec リポジトリに置く。kernel には手順と雛形だけがある（[ADR-00024](../adr/00024-refine-acceptance-with-bounded-review-rounds.md)）。spec リポジトリへの組み込み（ディレクトリ、雛形のコピー、エージェントが本手順を読める状態）は [PB-00021](00021-embed-workflow-in-spec-repo.md) で先に済ませる。

語彙は [ADR-00024](../adr/00024-refine-acceptance-with-bounded-review-rounds.md) に従う。**質問** = 未回答の欠落（`Q-n`）、**未決** = PdO が「決めない」と答えたもの。どちらも置き場はシートの「決められていないこと」欄。

## 手順

### 1. 入力を揃える

1. 要件（requirements.md、または Confluence の設計原文の URL とページバージョン）と、PdO が書いた design の節があればそれを入力として、受け入れ例シートの `要件（入力）` / `設計（参考）` に書く。エージェントが Confluence を読めない環境では、[PB-00021](00021-embed-workflow-in-spec-repo.md) 手順 3 で決めた経路（人が本文を貼る / エクスポートを commit しない読み取り用ファイルとして渡す）で本文を渡す。開発が書いた技術設計の値（タイムアウト、既定値、内部構造）は入力に含めない
2. 依拠した KB の ID を書く。まず**案件リポの `adr/`**、横断の決定だけ kernel の `adr/`（[ADR-00019](../adr/00019-kernel-and-project-layers.md)）。空なら開発が案件 `adr/` から列挙し、PdO には「業務上の決定が別にあるか」だけ確認する
3. シートの `承認:` は `未` のまま。記録（acceptance-refinement-log.md）の冒頭を埋め、入力の commit（または Confluence のバージョン）を書く

### 2. 初稿（エージェント）

4. 要件に**明記された**値だけを代表例・境界・反例・制約の行に落とし、各行の `出所` に `要件 <場所>` を書く。「以上 / 以下 / 未満 / 超 / 含む」が本文にあれば、その境界は明記扱いにする
5. 明記されていない閾値・境界・単位・不成立時の挙動・制約の値は、行を空欄にせず「決められていないこと」に**番号付きの質問**（`Q-1`, `Q-2`, …）として書く。質問は選択肢付きにする（「6 か月ちょうどは対象内か、対象外か」「退会済みはエラーか、割引なしで通すか」）。値を埋めてはいけない
6. どうしても候補を置きたい場合だけ `出所: 提案` で行を置く。組み合わせが多い例（ロール × 操作）は代表行だけ本表に置き、組み合わせは別表にする

### 3. レビュー巡（既定 3 巡）

各巡で 7〜12 を行う。レビュアーは初稿を書いたセッションと文脈を共有しないエージェント、または開発。**L5（テスト可能性）は各巡で開発が確認する**（レビュアーがエージェントでも）。

7. 入力の commit / バージョンが前巡から変わっていたら、`要件 …` 出所の行を差分と照合し、変わった行を P0 として指摘表に載せる。前巡の回答の書き戻し（出所更新）だけの差分は照合対象外。正本が Confluence なら版の比較は開発（人）が行い、比較 URL を記録に書く
8. 固定観点 L1〜L6（[ADR-00024](../adr/00024-refine-acceptance-with-bounded-review-rounds.md) §4）でシートを読み、指摘を等級（P0 / P1 / P2）付きで記録の「指摘」表に追記する。指摘には対象の行 ID（`境界-1` の形）か Q 番号を付ける。1 巡目は Q-n を参照するだけでよい。2 巡目以降の新規指摘は、前巡の回答と入力の変更に起因するものに限る
9. **P1 はその巡の中でエージェントか開発が直す**（行の分割、制約表への移動、表現の具体化）。PdO には回さない
10. 質問（Q-n と選択肢）を PdO の見える場所（PR コメント / Jira / Confluence のコメント）に提示し、シート本体は commit 固定の表示 URL（permalink）で示す。PdO が P0 に答える。答えは URL を持つ場所に書くか、口頭なら議事録 URL を残す（記録には URL と引用の両方）。答えは値・境界・挙動のいずれか、または「未決」。回答期限は既定 5 営業日（Confluence への書き戻しにも同じ期限）
11. エージェントが回答を反映する。反映した行の `出所` を `PdO <名前> YYYY-MM-DD <URL>` にし、**要件の正本に書き戻して `要件 <場所>` に更新する**。正本が requirements.md なら同じ PR で書き戻す。正本が Confluence なら PdO がページを更新し、出所に更新後のページバージョンを書く（requirements.md は持たず、リンクだけ）。「未決」は「決められていないこと」に残す。却下した指摘は理由を書く。期限を過ぎた未回答はそのまま「決められていないこと」に残して次へ進む
12. 記録の「対応」表に、指摘番号ごとの対応（反映 / 未決へ / 却下）、回答の引用または URL、決めた人、残りの P0 / P2 件数を追記する

13. 巡の終わりに P0 が 0 件なら終える。3 巡で残った P0 は「決められていないこと」に移す。**境界や不成立時の挙動が未決のままでは、その機能の実装を始めない**。進めたいときは PdO が `PdO 暫定 <名前> YYYY-MM-DD <URL>` を置く。4 巡目は作らない（続けるなら機能を分割し、新シートに旧記録のリンクと分割前の巡数を書く）

### 4. 承認と引き渡し

14. 承認の条件を確認する: P0 が 0、`提案` の行がない、`PdO …`（暫定以外）の行が `要件 …` に更新済み、制約表に空欄がない、「決められていないこと」が空か実装対象外として明示されている
15. シートの permalink を PdO に示し、PdO が承認する。シート冒頭の `承認:` に `PdO <名前> YYYY-MM-DD <URL>` を書く（PdO が git を使わなければ、承認コメントの URL 付きでエージェントが記録する。URL のない承認は書かない）
16. [PB-00013](00013-start-tdd-from-examples.md) へ渡す。実装スペックの要否は [PB-00012](00012-triage-implementation-spec.md)。Story の切り方は [PB-00022](00022-run-work-units-from-acceptance.md)。承認前の書き戻し PR の `Refs:` は Epic キー（[ADR-00025](../adr/00025-control-work-units-commits-prs.md) §2）

### 5. 再開と還流

17. 承認後に例を変えたいときは `承認:` を `未` に戻し、記録に「改訂 #n」の章を開いて巡を 1 から数え直す。旧巡は残す。実装中の Story は止め、改訂は別 PR（`Refs:` は Epic キー）で通してから再開する。表の `#` は再利用しない
18. 複数の機能・案件で同じ指摘が繰り返されたら（例: 「境界の 1 つ手前が常に抜ける」）、観点や雛形の改訂候補として [PB-00008](00008-bridge-sdd-spec.md) 方向 B で kernel に戻す。案件の業務値は戻さない

## 検証

- 受け入れ例の全行（制約表を含む）に `出所` があり、承認済みシートに `提案` の行がない。`PdO …`（暫定以外）の行は要件の正本（requirements.md か Confluence のどちらか 1 つ）に書き戻されて `要件 …` になっている
- 数値・日時の閾値ごとに境界の行（ちょうど / 1 つ手前）があり、ルールごとに反例の行がある
- 記録に巡ごとの指摘表と対応表があり、各指摘に対応・回答の URL または引用・決めた人が付いている
- 回答と承認がすべて URL を持つ
- KB の決定や他機能のシートと矛盾する項目が、シートの中で決着されずに未決（案件側）か [ledger/open-questions.md](../ledger/open-questions.md) に出ている
- 4 巡目が存在しない。分割した場合は新シートが旧記録を指している

## 失敗時

- PdO が質問に答えられない → 要件が決まっていない。`承認: 未` のまま止め、未決を spec 側に残す。エージェントが代わりに決めない。期限後は回答済みの行だけで進む
- 3 巡で P0 が減らない → 設計の粒度が大きすぎる。機能を分割し、分割後の単位で手順 4 からやり直す
- 未決の境界を残したまま実装が始まりそう → 止める。PdO の `暫定` か機能の実装保留のどちらかを選ばせる
- `出所` のない行、`提案` のまま承認された行、URL のない `PdO …` が見つかった → 承認を `未` に戻し、該当行を質問に戻す
- 例が多すぎてテストが遅くなりそう → 代表例だけを外側に置き、組み合わせは別表と内側のテストに降ろす（[PB-00013](00013-start-tdd-from-examples.md) 失敗時）
- 指摘が毎回同じ観点に偏る、または毎巡新しい論点が湧く → 2 巡目以降の範囲を前巡の回答起因に限る（手順 8）。それでも湧くなら機能を分割する。観点の不足が繰り返すなら手順 18 で kernel へ
- spec リポのエージェントが kernel を読めない → 案件作業は止めず、[PB-00021](00021-embed-workflow-in-spec-repo.md) の組み込みを先に直す
