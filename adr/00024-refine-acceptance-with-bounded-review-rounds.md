## 文脈

開発ループは `spec(SDD) → 受け入れ例 → テスト(TDD)` と置いているが（[README](../README.md)、[GUIDE](../GUIDE.md) §4）、手順があるのは「受け入れ例 → テスト」（[PB-00013](../playbook/00013-start-tdd-from-examples.md)）だけで、「PdO の設計 → 受け入れ例」の区間には担い手も終了条件もない（[EVID-00032](../evidence/00032-acceptance-examples-need-questions-provenance-bounded-rounds.md)）。[ADR-00014](00014-implementation-spec-split.md) は「ビジネススペックは受け入れ例まで落とす」と決め、PdO の負荷が上がることを代償として認めたが、負荷を受け止める工程は未定義である。

この区間にエージェントを入れ、SDD で運用中の spec リポジトリ（requirements / design / tasks を持つ）に組み込みたい。エージェントは値を推測で埋める（[EVID-00011](../evidence/00011-spec-first-reduces-rework.md)）ため、そのまま「例を書かせる」と、PdO が決めていない業務値が例の形で実装に流れる。

用語: 本 ADR の「PdO の設計」は [ADR-00014](00014-implementation-spec-split.md) の**ビジネススペック**（PdO が書く、基本設計〜詳細設計の一部）を指す。SDD リポでは多くの場合 `requirements.md`（受け入れ基準を含む）が正で、PdO が書いた design の節は補助である。開発が書く技術設計（タイムアウト値、既定値、内部構造）は入力に含めない。

## 決定

### 1. 置き場所 — 成果物は案件リポ、手順は kernel

| もの | 置き場所 | 理由 |
| --- | --- | --- |
| 受け入れ例シート、ブラッシュアップ記録 | 案件（spec）リポ。機能ごとのディレクトリに requirements / design と並べる | 案件固有の値であり kernel に入れない（[ADR-00008](00008-sdd-bridge.md)、[ADR-00019](00019-kernel-and-project-layers.md)） |
| 手順・雛形・skill | kernel（本リポ） | 他案件でも同じ工程を繰り返す |
| 案件横断で効く発見 | kernel へ昇格（[PB-00008](../playbook/00008-bridge-sdd-spec.md) 方向 B） | 昇格条件は変えない |

受け入れ例は**要件（requirements）の精緻化**である。回答で決まった値は requirements にも書き戻し、シートと requirements が別権威にならないようにする（§3）。design（どう作るか）の中には入れない。この位置づけは本 ADR の決定であり、[ADR-00008](00008-sdd-bridge.md) の対応表は変えない。

### 2. 役割 — エージェントは問い、PdO が決める

| 役割 | すること | しないこと |
| --- | --- | --- |
| エージェント | 要件に明記された値を例に落とす。欠落を**質問**に変える。固定観点でレビューし指摘を等級付きで出す。回答を URL 付きで反映し、requirements に書き戻す | 業務値を発明する。URL のない回答・承認を書く。設計や実装を書く |
| PdO | 質問に答える（値・境界・反例を決める）。承認する。回答と承認は URL を持つ場所（PR コメント / Jira / Confluence / 議事録）で行う | 例の体裁を整える作業を抱える |
| 開発 | 各巡で L5（テスト可能性）を見る。P1 を値を変えずに直す | 例の値を決める |
| レビュアー | 初稿を書いたセッションと文脈を共有しないエージェント（または開発） | 自分の初稿を自分で審査する |

承認は人の判断であり、エージェントが代わりに決めない。PdO が git を使わない組織では、PdO の回答・承認を**出典 URL 付き**でエージェントが記録してよい（[PB-00018](../playbook/00018-draft-evidence-from-sources.md) と同じ扱い。[ADR-00017](00017-machines-record-facts-humans-decide-status.md) の「機械は事実を記録する」の範囲）。URL のない回答・承認は記録しない。

### 3. 出所 — 各例の行に値の由来を持つ

受け入れ例の各行（代表例・境界・反例・制約）に `出所` を持たせ、次のいずれかを書く。

| 出所 | 意味 | 実装に渡せるか |
| --- | --- | --- |
| `要件 <場所>` | PdO の要件本文に明記されている。`<場所>` は要件 ID（`REQ-3`）か、パスと見出し（`requirements.md §2` / `requirements.md#割引`）。見出し番号がなければ見出し文字列でよい | 渡せる |
| `PdO YYYY-MM-DD <URL>` | 質問への回答として PdO が決めた。URL は回答の場所 | 渡せる。ただし同じ PR で requirements に書き戻し、`要件 …` に更新する（一時状態） |
| `PdO 暫定 YYYY-MM-DD <URL>` | PdO が暫定値を置いた。確定は別途 | 渡せる。テストに `暫定` の印を付ける |
| `提案` | エージェントの候補。PdO 未確認 | **渡せない**。承認前に `PdO …` に変わるか、削除されるか、未決へ移る |

「明記されている」の判定: 要件本文に「以上 / 以下 / 未満 / 超 / 含む / 含まない」が書かれていれば、その境界は明記扱い（`要件 …`）。それ以外の境界・不成立時の挙動・単位は質問にする。

### 4. 有限回 — レビュー→修正は既定 3 巡、1 巡に回答期限を置く

各巡は「入力の差分確認 → 固定観点でのレビュー（指摘表）→ PdO の回答 → 反映と書き戻し → 記録」の 1 往復とする。

固定観点:

| 観点 | 問い |
| --- | --- |
| L1 具体性 | 入力と期待結果が具体値か。「適切に」「など」「正しく」「速やかに」が残っていないか |
| L2 境界 | **数値・日時の閾値**ごとに「ちょうど」「1 つ手前（単位つき: 日 / 月 / 円）」が対象内 / 外で書かれているか。列挙値・真偽は L3 で扱う |
| L3 反例 | ルールごとに不成立の入力と、そのときの挙動（エラー / 無視 / 既定値）があるか |
| L4 無矛盾 | 例同士、要件本文、依拠した KB の決定、**同じ spec リポの他機能の承認済みシート**と矛盾しないか |
| L5 テスト可能性 | 1 行 = **1 つの操作に対する 1 回の観測**（複数の確認項目はあってよい。別の操作・別の前提を混ぜない）。内部構造に触れていないか。前提状態が明記されているか |
| L6 分離 | 性能・可用性・データ量は制約表へ。画面の**状態**（空 / 読込 / 権限なし / エラー）の名前と結果は例に残し、レイアウト・文言・余白だけを Figma 等へのリンクにする（[PB-00016](../playbook/00016-large-project-usage-map.md) §5） |

等級と帰結:

| 等級 | 意味 | 誰が閉じるか |
| --- | --- | --- |
| **P0** | PdO の決定がないと閉じない（値・境界・挙動の欠落、矛盾） | PdO が答える |
| **P1** | 値を変えずに直せる（行の分割、制約表への移動、表現の具体化、出所の補記） | エージェントまたは開発が**その巡の中で**直す。PdO の回答は不要 |
| **P2** | 体裁 | 巡の外で直してよい |

停止条件:

- 巡の終わりに **P0 が 0 件**なら終える（P1 は巡内で閉じるので残らない）
- 1 巡の回答期限は既定 **5 営業日**（案件で上書き可）。期限を過ぎたら、回答済みの行だけで次に進み、未回答は「決められていないこと」に残す
- 2 巡目以降の新規指摘は、前巡の回答と入力の変更に起因するものに限る（範囲を広げない）
- 3 巡で残った P0 は「決められていないこと」に移す。**境界や不成立時の挙動が未決のままでは、その機能の実装を始めない**（実装者が境界を決めることになるため）。進めたいなら PdO が `PdO 暫定` を置く
- 4 巡目は作らない。続けたいときは機能を分割し、新しいシートに旧記録へのリンクと分割前の巡数を書いて、巡を 1 から数え直す

巡回数 3・回答期限 5 営業日・観点 6 つは経験則であり、測定して見直す（[OQ-00040](../ledger/open-questions.md)）。

### 5. 可視化 — 指摘と対応を同じ表に残す

初稿の質問には番号（`Q-n`）を振る。各巡の指摘（等級・観点・内容・対象行または Q-n）と対応（何をしたか・回答の引用または URL・決めた人・反映 / 未決へ / 却下）を、ブラッシュアップ記録（[templates/acceptance-refinement-log.md](../templates/acceptance-refinement-log.md)）に**追記**する。巡の数は記録だけが持つ。記録は受け入れ例と同じディレクトリに置き、後から「何が指摘され、何を直し、何を決められなかったか」が巡ごとに読めるようにする。

### 6. 承認と引き渡し、再開

- 承認はシート冒頭の `承認:` 欄に `PdO YYYY-MM-DD <URL>` を書くことで表す（KB の `status` とは別の欄であり、語彙も別）。未承認は `未`
- 承認の条件: P0 が 0 件、`提案` の行が残っていない、制約表に空欄がない（空欄は質問にする）、「決められていないこと」が空か実装対象外として明示されている
- 承認後に例を変えたいときは、`承認:` を `未` に戻し、記録に「改訂 #n」の章を開いて巡を 1 から数え直す。旧巡は残す
- 承認後は [PB-00013](../playbook/00013-start-tdd-from-examples.md) へ渡す。実装スペックの要否は [PB-00012](../playbook/00012-triage-implementation-spec.md)。組み合わせが多い例（ロール × 操作など）は代表行だけ本表に置き、組み合わせは別表にする

## 根拠

- [EVID-00032](../evidence/00032-acceptance-examples-need-questions-provenance-bounded-rounds.md): 欠落は質問に、値は出所付きに、往復は有限回に。外部の方法論（Example Mapping）と本リポジトリのレビュー記録が同じ構造を持つ
- [EVID-00011](../evidence/00011-spec-first-reduces-rework.md): 仕様の空白はエージェントの推測で埋まる
- [EVID-00018](../evidence/00018-tests-outlive-design-docs.md): テストを正本にできるのは例まで落ちた受け入れ条件だけ

## 結果・トレードオフ

- 利点: 「設計 → 例」の区間に担い手・観点・終了条件が付き、[ADR-00014](00014-implementation-spec-split.md) の分解が上流で成立する
- 利点: PdO の負荷が「例を全部書く」から「質問に答える・承認する」に変わる。P1 は PdO に回らない
- 利点: 出所列と URL により、承認者はどの値を自分が決めたかを表から読める。提案のまま実装に流れない。回答は requirements に書き戻されるので二重権威にならない
- 利点: 記録が巡ごとに残るため、指摘と対応が後から監査できる
- 代償: PdO の回答待ちが工程のボトルネックになる。期限で部分承認に進めるが、未決の境界は実装を止める（止まるのが正しい）
- 代償: 巡回数 3・期限 5 営業日・観点 6 つは経験則であり、未測定。多すぎれば形式化、少なすぎれば解釈が残る
- 代償: 案件リポに雛形を 2 つ置き、requirements への書き戻しという作業が増える
- 代償: kernel の skill を案件リポのエージェントへどう届けるかは未決（[OQ-00041](../ledger/open-questions.md)）。それまでは案件 `AGENTS.md` から kernel の URL を参照する
