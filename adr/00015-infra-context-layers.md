## 文脈

エージェントに DB やインフラの作業をさせるとき、何を文脈として渡すべきかが定まっていなかった。素朴にやると「現在の構成」を Markdown にまとめることになるが、[EVID-00020](../evidence/00020-infra-state-rots-fastest.md) のとおり状態は鮮度検査が追いつかない速さで腐り、腐った文書は無いより有害である。

一方で「なぜこの構成にしたか」は取得コマンドでは出てこず、人が残すしかない。両者を同じ文書に入れているのが問題である。

## 決定

### 1. 3 層に分けて正本を別に置く

| 層 | 例 | 正本 | KB に入るか |
| --- | --- | --- | --- |
| 制約 | 整合性モデル、テナント分離方式、RPO / SLO、リージョン構成 | KB の `adr/` | 入る |
| 根拠 | 負荷試験の結果、障害の事後分析、移行の実測 | KB の `evidence/` | 入る |
| 契約 | DDL、マイグレーション、IaC 定義、スキーマ | コード / IaC リポジトリ | 入らない（ID とリンクのみ） |
| 状態 | インスタンス数、パラメータ実値、行数、コスト | 実行して取得 | **入らない** |

### 2. 状態を文書化しない

- 構成図・環境一覧・パラメータ表を手で書かない。必要なら定義ファイルから生成する
- 生成物であっても、変わるたびに再生成できないものは作らない
- すでにある状態記述は削除し、そこに混ざっていた「なぜそうしたか」だけを ADR として救出する

### 3. エージェントへの渡し方

| 必要なもの | 渡し方 |
| --- | --- |
| 守るべき制約 | KB の ADR を読ませる（Tier 2） |
| 制約の理由 | KB の evidence を読ませる（Tier 3） |
| 現在の状態 | **playbook に書いた取得コマンドを実行させる** |

playbook が持つのは値ではなく**値の取り方**である。状態はリポジトリに常駐させない。これは [ADR-00006](00006-context-tiers.md) の Tier の考え方の延長で、状態は Tier 3 よりさらに外側——必要になった時点で取りに行く情報——として扱う。

### 4. 可逆性で進め方を変える

- **可逆な変更**（インデックス追加、パラメータ調整、インスタンスサイズ）は事前設計せず、試して測る。測定結果は evidence として残す
- **不可逆な変更**（テーブル分割、シャーディングキー、リージョン、公開契約）だけ事前に ADR を書く

判定基準は [ADR-00014](00014-implementation-spec-split.md) の実装スペックの条件と同一である。

### 5. 優先して残す evidence

インフラ領域で最も長持ちするのは**失敗の記録**である。「この構成でこの規模でこう壊れた」は構成が変わった後も有効だが、「現在こういう構成です」は数か月で無価値になる。障害と負荷試験を優先して evidence にする。

## 根拠

- [EVID-00020](../evidence/00020-infra-state-rots-fastest.md): 状態は 90 日の鮮度検査で守れない速度で腐り、かつ実行して取得できる
- [EVID-00019](../evidence/00019-change-cost-is-asymmetric.md): 可逆な領域では実測が事前設計に勝ち、不可逆な領域だけ理由を残す価値がある
- [EVID-00009](../evidence/00009-context-budget-is-finite.md): 文脈は有限予算で、頻繁に変わる巨大な表を常駐させると正しい情報の割合が下がる

## 結果・トレードオフ

- 利点: インフラ文書の分量が減り、残ったものが腐らなくなる
- 利点: エージェントが古い構成情報を前提に作業する事故が構造的に起きなくなる
- 利点: 「何を書けばいいか分からない」が「制約と失敗だけ書く」に縮む
- 代償: 状態を知るたびにコマンド実行が必要で、権限やネットワークが制限された環境では取得できないことがある。その場合は取得できない事実自体を open-questions に残す
- 代償: 監査で特定時点の構成証跡が要る場合、別途スナップショットを生成する仕組みが要る（本 ADR は手書き文書を禁じるだけで、生成物を禁じない）
- 代償: 既存の構成ドキュメントを整理する初期コストがかかる
